# Packaging, boot, updates and the launcher

Packages `@talos/shell` (ServiceWorker + installer), `@talos/launcher` (supervisor), tool
`tools/package` (release assembly). Entry points: `packages/shell/src`,
`packages/launcher/src` (`Supervisor`), `tools/package/build.ts`, `tools/package/e2e.mjs`,
server `modules/ops` (update staging). Operators' how-to for the Chinese README shipped in
the release is generated by `tools/package/build.ts`.

## Principles

A release is a folder with no host prerequisites. The official Node runtime is bundled
(pinned version in `tools/`, currently v24.22.0, downloaded from nodejs.org and checked
against that version's `SHASUMS256.txt`, cached and re-verified on every assembly;
`TALOS_RUNTIME_CACHE` moves the cache).

**Legacy importer.** `tools/migrate/build.mjs` bundles the importer (`@talos/migrate`) with esbuild into `migrate.js`, the same way as `server.js` (same external native addons, resolved from the release's `node_modules`). It ships inside every release, so it is part of the `-update.zip` too. `migrate.cmd`/`migrate.sh` at the install root read `current` and run it with `runtime/node`; usage in `docs/impl/ops-migrate.md`.

**Native addons.** `better-sqlite3` and `sharp` are N-API (independent of the Node ABI) and
cannot be bundled, so `server.js` imports them externally from the release's own
`node_modules/`. `tools/package/native.ts` assembles that directory per target from the
pnpm-installed packages and nothing else: better-sqlite3 `package.json`, `lib/` and the single
`prebuilds/<platform>.node`; sharp (`dist/`), its pure-JS dependencies, `@img/sharp-<platform>`
and, on Linux, `@img/sharp-libvips-linux-x64` (Windows ships libvips DLLs inside
`@img/sharp-win32-x64`). Both Linux targets use the glibc `linux-x64` binaries. pnpm
`supportedArchitectures` (workspace file) installs the win32 packages on Linux so the lockfile
pins their tarball integrity and the pnpm store makes assembly offline-capable; no prebuild
download runs at package time. `native-manifest.json` pins SHA-256 of every `.node`, `.dll` and
`.so`; assembly fails on a mismatch, a missing pin or any file named for another platform. Sync replica worker threads (`server.md`) load the same `server.js` and the same addon binaries; a release ships no extra files for them.

## Shell: boot and offline assets (`@talos/shell`)

Dependency-free (no `@talos/base`; `ShellError` has the `AppError` wire shape and the client
boot boundary maps it). No Cache Storage: the ServiceWorker serves the shell document and
`/app/<build>/*` assets from IndexedDB (`talos-shell`: `assets` keyed `[build, path]`, `meta`
with active/pending/previous/bootAttempts/activation, `builds` with the exact manifest and a
complete flag), cache-first, and a stalled network can never block start-up. The worker
handles only navigations and same-origin `/app/<build>/` GETs; `/link`, `/dl/` and
`/app/manifest.json` are never touched. It takes over at once (`skipWaiting`, `clients.claim`)
while the application version is governed purely by IndexedDB metadata. It is bundled as a
classic ES2017 script with no polyfills and requires HTTPS or localhost.

**Install.** The manifest `{build, assets:[{path,size,sha256,mime}]}` lists canonical
`/app/<build>/...` paths with `index.html` mandatory. The installer downloads sequentially
(`no-store`, same-origin credentials, redirects rejected), checks each asset against size and
WebCrypto SHA-256 before one bounded write transaction per asset (never a transaction across
networking or hashing; 64 MiB per asset by default), and on retry rehashes stored assets and
skips the correct ones. A build id is immutable: changed or reordered manifests need a new id.
A final transaction verifies every asset is present and marks the build complete and active
(first install) or pending (update). Failed downloads stay resumable and can never become
active. Explicit pruning removes unprotected builds; a concurrent install detects pruning and
fails instead of publishing an incomplete version. All shell writes pass a plain-data guard.

**Activate and roll back.** A downloaded pending build stays staged across reloads; **reload
alone does not authorise an update**. The user's confirmation records a separate activation
request (`apply()`, state `applying`, the caller reloads). On navigation the worker consumes
that request, promotes the pending build and records an unconfirmed boot. The previous build
is kept until `confirmBoot(build)` (which must name the current active build, so stale tabs
cannot confirm another version); two navigations without confirmation roll back to the last
known good build. Rollback counts navigations across tabs rather than guessing health from
elapsed time; the client confirms only after React has committed a stable gate. Installed
assets are integrity-checked on serving; a corrupt or missing one yields an immediate 503 so
later boots reach rollback. The manifest endpoint is always network-backed. A build change is
detected through WELCOME (not independent polling), after the server restarted into the new
release. Release assets contain only the installable shell and manifest assets; the gallery
and diagnostics are development-only.

## Release layout and launcher

The install directory is the working directory of the launcher and the server, and every
relative path (including certificate paths) resolves against it. Each top-level directory
holds one kind of thing, so an operator can tell at a glance what may be moved, cleared or
must be kept:

```
runtime/node[.exe], launcher.js, target     bundled runtime, supervisor, package target
config/       operator configuration only: config.json (settings), model.json (AI provider)
data/         business data only: talos.db, objects/ (with upload stages/trash), backups/
logs/         operator logs: launcher.log (rotated), server.jsonl
tmp/          operator scratch: downloaded/staged updates and the rollback backup,
              versions being unpacked, server temp files (document conversion spool)
versions/     <build>/ immutable server.js, migrate.js, client/, shell/, vendor/, release.json;
              current (UTF-8 pointer FILE, never a symlink), state.json (atomic durable
              commit record: pending deadline, rollback path), launcher.lock (PID lock)
migrate.cmd, migrate.sh   run versions/<current>/migrate.js with the bundled runtime
```

Rules (`packages/launcher/src/install/layout.ts`, shared by launcher and server):

- **Everything non-operational is in `data/`**; nothing operational is. Backups are business
  data. The server's own lock is `data/server.lock` (it guards the database, also against an
  offline restore).
- **`config/` is passed as the first argument** (`launcher.js [config-dir]`,
  `server.js restore <backup> [config-dir]`), default `config` under the working directory.
  A missing `config.json` means defaults; a missing `model.json` means no AI.
- **`dataDir`, `logsDir`, `tmpDir` may be moved in `config.json`**; `versions/` and the
  config directory are fixed. Launcher and server read the same keys with the same resolver,
  so a moved data directory is also what rollback restores.
- **`tmp/` may be cleared while stopped.** A version is unpacked under `tmp/versions/` and
  moved into `versions/` whole (copied beside first when `tmp/` is on another volume).
- **Old versions are deleted on confirmation**: once the candidate is confirmed nothing can
  roll back to the previous version, so every other version directory goes; a rolled-back
  candidate is deleted too (so the same update can be staged again), and a boot without a
  pending update prunes leftovers.

The launcher forks `server.js` with an IPC channel and sends one `{type:"start", config}` message
(config directory, client and service-worker paths, `launcher: {target, updatePending}`;
`server.md`). The server reads no environment variables; yt-dlp and its plugin are found at
`vendor/media/` next to `server.js`. Rollback runs `server.js restore <backup> <config-dir>` of
the previous version. Everything the server and the launcher print, errors included, reaches the
console as well as `logs/launcher.log`; a server that keeps failing to start is restarted with
backoff (also when the restart itself fails), so the console shows why.

`@talos/launcher` is bundled so installed releases need no npm modules; it depends only on
`base` and zod compiled in, plus two small public APIs shared with the server: the archive API, so the
server's preflight validation and the launcher's final validation use identical ZIP rules, and the
start-message schema and the install layout (these are the server-to-launcher edges). In-app updates
do not replace the launcher, so a new release's `server.js` must keep accepting the start message an
older launcher sends. The `config/`/`versions/` layout was a deliberate break: installs from before it
are re-extracted from a full package (move the old `data/` across); an older launcher that applies a
newer update gets a server that rejects its start message, and rolls back.

- **Atomic pointer, not symlinks or directory swaps**: `versions/current` is a pointer file
  repaired from the durable state record after a crash; no directory is renamed over running
  files (Windows-safe). Data lives outside every version.
- **Staging** verifies the ZIP, the target, manifest cardinality, every SHA-256 and size
  before publishing a new release directory; duplicate builds are rejected. ZIP32 only,
  STORED or DEFLATE, 512 MiB archive, 1 GiB expanded, 512 MiB per entry (checked before
  inflation); paths reject traversal, drive prefixes, control bytes, symlinks, duplicate or
  case-colliding names, Windows device names and trailing dots/spaces. SHA-256 establishes
  integrity, not publisher identity; uploads need a root session and cloud manifests/downloads
  require HTTPS; at most 5 redirects are followed (GitHub latest/download redirects to its object host), each HTTPS only, with bounded bodies and deadlines.
- **Candidate confirmation**: after apply, the new release must be confirmed (`ops.update.confirm`
  by root after checking the client; only the current child can confirm itself) within the original
  three-minute deadline, which a launcher restart never resets. A candidate
  crash or the deadline restores **both** the previous release and the pinned complete
  backup taken at staging (business writes during the window are lost by design).
- **Supervision**: children stop over IPC first with a 10 s kill deadline; crashes back off
  from 500 ms to 30 s; SIGINT/SIGTERM/SIGHUP drain the child and release the lock (Windows
  console close is best effort). A stale launcher lock needs the operator to check the PID;
  locks inside `data/` reclaim dead PIDs. Logs keep the current and previous 2 MiB files and
  tolerate broken stdout.
- **Targets**: ids `win32-x64`, `linux-debian-x64`, `linux-redhat-x64`. The installation's
  `target` file is immutable across updates and rollback; the server and the launcher both
  reject an update for a different target, naming expected and received ids, before backup
  or extraction. Each release carries only its own renderer under `vendor/pdfrender/<flavour>`
  with a `target` selection file and no fallback. Linux builds link system libraries
  dynamically (list: `vendor/pdfrender/README.md`; `docpipe doctor` reports gaps).
- Full installs contain Node and launcher; in-app update ZIPs replace only versioned
  server/client/helper payloads, so updating Node or the launcher requires a new full install
  with data and configuration carried over.

## Assembly (`pnpm package`)

Builds every workspace artifact and writes to ignored `dist/release/`: `full/` holds the
installs (`.zip` for Windows, `.tar.gz` for Linux, recording native executable modes);
`update/` holds the per-platform `-update.zip` with `release.json` and a `.zip.json` cloud
manifest (`{v, build, url, size, sha256}`, relative url). CI uploads the two directories as
separate artifacts (`talos-update-<target>`, `talos-full-<target>`), each uploaded from inside
its directory so the release job merges them into one flat set of assets.

**Publishing.** A release is cut only by running the `build` workflow manually on `main` with a
`version` input (`MAJOR.MINOR.PATCH`, e.g. `1.0.2`); there is no tag trigger. After `check` and
all three packages pass, the release job refuses an existing tag or release, creates `v<version>`
on the exact packaged commit together with the GitHub release (generated notes, marked latest),
and uploads every asset plus `SHA256SUMS`. The build id stays the commit's short hash (launcher
build ids allow no dots, and an installed launcher validates every update's id). The job
also publishes a fixed-name `talos-<platform>-update.json` whose url is the absolute versioned
asset, so `releases/latest/download/talos-<platform>-update.json` always names the newest
update; the server uses it when no manifest URL is configured (cloud updates stay opt-in). `--target <id>` or `TALOS_PACKAGE_TARGET`
builds one. Only Node scripts do downloads and archive work (no tar/unzip/curl). yt-dlp is a
pinned version with per-platform SHA-256 verified at package time (`tools/package/media-binary.ts`, whose
cache `pnpm dev` shares). Installs include default
config, `start.cmd`/`start.sh`, `migrate.cmd`/`migrate.sh`, opt-in Task Scheduler / systemd user-service helpers, licences
and the operator README. `TALOS_BUILD_ID` selects the build id (safe ASCII).

Verification: `tools/package/e2e.mjs` (part of `pnpm e2e`) packages A and B for the host
target and B for the other Linux target, checks renderer isolation, manifests, start scripts
and modes, wrong-target rejection by launcher and server, launcher A to B confirmation,
browser WELCOME + ServiceWorker install, rollback of a broken C, backup/mutate/restore
including objects, and HTTPS + WSS with a generated certificate (OpenSSL is a test-only need).
`windows-smoke.mjs` runs the Windows package under Wine (serving the client and converting a
PDF; handler/IPC cleanup, not native console events). Native Windows, COM and console-close
behaviour are not covered by any gate.
